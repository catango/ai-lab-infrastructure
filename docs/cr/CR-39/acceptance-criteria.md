# CR-39 Acceptance criteria

Verified by the implementation PRs in `ai-software-template` (see the plan). "CI" means a green run of the named template job. "Both architectures" means the workspace (x86-64) and the template's CI job on `ubuntu-24.04-arm`. The criteria are proposed and become binding when the design PR is merged. T-16 is the baseline Stage 5 exit criterion.

| ID | Criterion | Evidence |
|---|---|---|
| T-1 | Every tracked payload file has exactly one class (`owned`, `seeded`, or `zoned`) in `.template/manifest.toml`; a file without a class, with two classes, or a `zoned` file without its markers fails the gate. | Template job `manifest` with a passing tree and one failing fixture per case |
| T-2 | Generating from the template (export without history, then `initialize-project` with placeholder values) yields a repository with no `template-dev/`, no unfilled placeholder, and a green `./scripts/quality-gate.sh --strict`. | Template job `generate` on x86-64 |
| T-3 | T-2 also passes on ARM64, and the generated `ci.yml` carries the job `quality-gate-arm64`, which is skipped when the repository cannot use a hosted ARM64 runner (`visibility: private`). | Template job `generate` on `ubuntu-24.04-arm`; fixture test of the skip condition |
| T-4 | `CLAUDE.md` has both zone markers exactly once, its owned zone matches the manifest hash, and the owned zone contains the instruction-trust rule and every Never-list item; the file is within its size budget. | Gate check `claude-md`, one passing and several failing fixtures |
| T-5 | `.claude/settings.json` contains every entry of `.claude/required-deny.txt`; deleting one entry fails the gate. The list equals the ADR-001 section 5 deny rules as recorded in this repository at the recorded commit. | Gate check `deny-list`, fixture test; provenance line in the manifest |
| T-6 | Each rule file has valid path scoping and is within its size budget; `public-repo.md`, `bash.md`, `workflows.md`, `docs.md`, `arm64.md`, and `operator.md` exist, and `operator.md` states the ADR-011 and CR-18 operator-script rules. | Gate check `size-budget`; rule-file test |
| T-7 | `scripts/new-cr <n> <slug>` creates the five-file CR skeleton and refuses to overwrite; `cr-layout` passes it, and fails a CR with a missing file, a duplicate criterion ID, or a plan row without a criterion ID. `docs/adr/_template.md` has the ADR header and sections. | Gate check `cr-layout` fixtures; script test |
| T-8 | In the generated repository `pr-contract` applies PC-1 to PC-7 for design, implementation, change, and template-sync PRs with the same results as the fixtures of this repository; PC-8 is inactive while the operator set in `config/project.yaml` is empty and active when it is not. | Fixture tests in job `skills` |
| T-9 | `template-sync` from version A to B replaces unchanged `owned` files and owned zones, adds new files, never changes a `seeded` file, updates `.template/state.toml`, and a second run changes nothing. | Template job `sync` |
| T-10 | `template-sync` skips a locally changed `owned` file or zone and lists it as a conflict in the PR body; it rejects a target that is not a tag, or whose commit is not contained in the template's default branch; no workflow, in the template or the payload, runs it. | Template job `sync`; negative fixtures; workflow scan in the gate |
| T-11 | `review-threads` outputs only threads and comments authored by `approver_login` from `config/project.yaml`, compared exactly (a similar login, a bot, and the machine account are excluded and only counted); it contains no call that resolves a thread, submits a review, or merges. | Fixture test with approver, machine-account, bot, and look-alike authors; static check of the script's calls |
| T-12 | `pr-checkpoint` reads and edits only the text between the checkpoint markers, updates the PR body with the REST PATCH call, and marks ready with the GraphQL mutation; none of its calls is `gh pr edit` or `gh pr ready`. | Fixture test; static check. The same calls run on the workspace in the implementation PR. The check on the lab VM is deferred to Stage 6 and recorded as open until then |
| T-13 | Each Skill in design section 6 exists as `SKILL.md` within its size budget, names a script that exists, and every script has `--fixture` or `--offline` and a test; `initialize-project` creates no label, ruleset, repository, or setting (it prints proposals). | Gate check `size-budget`; job `skills`; static check of `initialize-project` |
| T-14 | The template's CI runs the gate with all generic and template checks and the template jobs `manifest`, `generate`, `sync`, `skills`, and `leak`; every workflow passes the workflow-policy and no-Claude-in-workflows checks. The design's ADR-009 and ADR-010 assumptions (section 11) are the ones implemented, and a deviation is reported. | A green template CI run on a test PR; the section 11 table checked in the final implementation PR |
| T-15 | A scan of the template and of a generated tree finds no identifier pattern (tenancy or resource OCIDs, IP addresses, emails, keys, fingerprints, tokens); `public-repo-hygiene` runs for `visibility: private` too; a seeded identifier makes it fail. | Template job `leak`; fixture test |
| T-16 | **Stage 5 exit (baseline section 6).** The throwaway-repository dry run of design section 12, steps 1 to 10, passes on both architectures and writes a report with one line per step; the approver reviews the report. If Q11 requires it, the approver also completes a real "Use this template" run. | The dry-run report in the last implementation PR; the approver's review; for the real run, the approver's note in that PR |

Entry to Stage 5 also needs ADR-009 and ADR-010 approved. This CR delivers ADR-008 only, and none of these criteria covers the other two.
