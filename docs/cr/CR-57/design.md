## 2. Givens (approver)

G-1 Claude Desktop on the Windows client opens SSH sessions to the AI lab; Claude Code runs there as the AI user; the client may also hold SSH access to the operator machine; no local Claude Code on Windows. G-2 AI lab: Debian 13, x86-64; the AI user is configured, has a writable home, basic packages, and no sudo; a separate non-AI lab admin has sudo; the AI lab may reach project-specific resources configured by the project. G-3 Operator machine: a fresh Debian 13 x86-64 VM with internet access, provided outside the platform, with the operator user (no sudo; runs scripts that gather facts and apply changes; may reach production environments) and the operator admin (sudo) reachable over SSH. G-4 The operator machine is never an AI workspace. G-5 The platform names no host, address, user, or key. G-6 The AI lab is a VM hosted on the jump host (the lab host) and reached through it by ProxyJump; the lab host is outside the platform and is not the operator machine. G-7 Configuration scripts run only on the AI lab and the operator machine. G-8 The Windows SSH client is outside the platform. G-9 Egress design and filtering come from another project; SSH hardening of both machines is a platform requirement. G-10 The lab admin applies all AI lab configuration; the operator admin applies all operator configuration; the AI user and the operator user apply none. G-13 Each AI lab is a disposable VM for exactly one project (this repository counts as one); provisioning is outside the platform; the platform starts from a given Debian 13 x86-64 VM with the AI user and the lab admin reachable over SSH. G-14 Each managed account's public key is provisioned with the VM; any additional key fails the setup; no fingerprint confirmation is required. G-15 The operator machine is not reachable from the lab host and so not from the AI lab; the AI lab cannot reach services on the lab host; the hosts the AI user needs (PA-18), GitHub, and the environments the operator scripts need are reachable; the AI lab's SSH host keys are new on every rebuild. G-16 One operator machine serves this repository and every project. G-17 The operator machine is long-lived; a rebuild is a fresh VM plus the operator configuration; it holds no persisted credential (OC-4), so a rebuild loses only the output directories. G-18 Provisioning destroys an AI lab's disk when the lab is discarded (confirmed).

G-11 and G-12 are not in the review (discarded items); the numbers are not reused.

## 4. Decisions

PA-1 to PA-12 are the first draft's decisions as the review changes them; PA-13 to PA-46 are the review's. The numbers PA-27, PA-29, PA-32, PA-33, and PA-35 are not in the review (discarded) and are not reused.

**PA-1 Purpose.** The platform is two things: **preconfigured AI** (user-level and project Claude Code settings, rules, Skills, guardrails, the instruction-trust rule) and **integrated GitHub workflows** (the PR-centric workflow and `pr-contract`, the CI and security baseline, the software template, the machine-account model). It also provides the lab setup and the operator contract (ADR-012). It provisions no infrastructure and prescribes no technology stack.

**PA-2 An AI host is one project's disposable AI lab** per G-2 and G-13 that meets the lab contract (PA-15). The user owns the VM's provisioning, its addresses, and its keys; the platform names none.

**PA-3 Replaced by PA-19.** (The first draft's rule that Claude Code opens no onward SSH and never reads `~/.ssh/` is restated and enforced in PA-19.)

**PA-4 Trust zones.** Z0 (Windows client), Z1 (AI lab: AI user and lab admin), Z3 (GitHub), Z5 (Anthropic), Z6 (operator machine: operator user and operator admin), Z8 (lab host, outside the platform). Z2, Z4, and Z7 are removed. Z1, Z6, and Z8 are detailed in ADR-012. B1 is generalised: AI hosts cannot approve, merge, change settings, or change infrastructure. B3 keeps the operator clause, generalised. The T2 and T3 rows stay, on Z6.

**PA-5 Guardrails.** (Amended by follow-up R-2, section 13.3: where an organisation policy outranks the managed file, the deny rules are also carried by the user-level deny layer, PA-47.) On the AI lab the guardrails live in managed settings only. RR-8 is restated as: a user or repository setting can tighten but never relax the managed settings. The existing generic infrastructure-apply deny entries (`terraform`, `tofu`, `oci`) stay in the core list. The plan names the PR that puts them into managed settings (implementation step 2): they are copied there, and the repository files and the core list keep them (PA-A10 allows added deny lines only).

**PA-6 Lab setup and the token step replace the workspace restore.** D16 keeps its two rules (nothing durable lives only on a host; Claude Code configuration lives in repositories). AC1-7 becomes a timed run from VM handover (lab setup, token step, lab check) with a target of 15 minutes, excluding the time to type T1.

**PA-7 Toolchain.** The gate tools are installed by lab setup; ADR-005 is amended per PA-24.

**PA-8 Everything technology-specific is the project's.** Project resources reach the AI lab through the network project and PA-13; production work runs on the operator machine. Toolchain pins, build and deploy commands, lab connection notes, and technology deny rules live in the project repository through the template's seams (`docs/PROJECT.md`, `docs/PLATFORM.md`, `.claude/deny.platform.txt`, the CI manifest, `config/project.yaml`; ADR-008 decisions 1, 6, 8, 14).

**PA-9 ADR-002 is superseded; ADR-011 is amended (PA-23); ADR-012 is added (PA-46); CR-18 is closed (Q6).** The decision index also marks CHG-002 superseded. ADR-001 and ADR-005 are amended. Baseline v0.2 (Q4, PA-38, PA-40) marks CHG-002, D2 to D7, D12, D15, and D16 superseded or reduced.

**PA-10 PC-8 is active here**, with the paths of Q2.

**PA-11 Order of removal** (unchanged from the first draft). The repository `CLAUDE.md` keeps a rule until the PR that removes its subject; the aggregate `quality-gate` is green after each PR; required check names (`pr-contract`, `quality-gate`) do not change, so no ruleset edit is needed. PA-26 makes the order strict.

**PA-12 Name and role.** The repository keeps its role as the source of the platform's records, `pr-contract`, the generic gate checks, and the user-level AI configuration; the template stays separate. No code hardcodes the repository name (values come from `config/project.yaml`). The repository is renamed per Q3.

**PA-13 Credential placement.** The AI lab holds T1 and project-scoped non-production credentials recorded in the project's PROJECT.md (PA-43). Production and infrastructure-changing credentials, T2, and T3 exist only on the operator machine, used by reviewed scripts from a release tag, prompted or short-lived. No credential of the personal account is on the AI lab. The lab admin and the operator admin hold no credentials.

**PA-14 Accounts and keys, enforced on the servers.** Four accounts (AI user, lab admin, operator user, operator admin), each with its own key; no key is shared between accounts on a machine (checked). The lab admin, the operator user, and the operator admin use sk-ssh-ed25519 keys with verify-required if the Windows client supports them, otherwise passphrase-protected file keys. The AI user's key has a passphrase if Claude Desktop can use one, otherwise none (RR-P6). The lab setup PR records which applies.

**PA-15 Lab contract** LC-1 to LC-15 (ADR-012 section 4; LC-5 is not defined). If a Claude Desktop session on a set-up lab needs a forwarding or key permission beyond LC-11 and LC-13, only that named permission is added, with the reason recorded in the PR.

**PA-16 Lab setup** is the Ansible lab profile (PA-31), run by the lab admin from a clone the admin owns at a release tag; dry run by default (check mode with diff); idempotent. On a fresh VM it accepts the one provisioned key of the AI user and of the lab admin, and fails when a managed account has no key or more than one, a key is shared between accounts, root or any other account has a key, the AI user's `~/.ssh` holds a private key, or `AuthorizedKeysCommand`, `TrustedUserCAKeys`, or `AuthorizedPrincipalsFile` is set. The checks fail when sshd reads keys from any location other than the root-owned one, and warn on an inert leftover `authorized_keys` file in a user's home (round 2, X-1). It applies: archive prerequisites; the gate tools into `/opt/ai-lab`; root-owned managed settings and a managed CLAUDE.md carrying the settings of `workspace/claude-user/` and the non-relaxable rules of its CLAUDE.md (merged, never replaced; round 3, C-8); the system-wide git identity; the provisioned keys copied to the root-owned authorized-keys location, with sshd switched only after a second login with each account is confirmed while the current session stays open; LC-13; unattended security updates; project toolchains and package lists (PA-34); and the root-owned token step and lab check. It prints the host key fingerprints for information, removes nothing, writes nothing into a user's home, and never executes from a path the AI user can write.

**PA-17 What the user runs on the AI lab.** Logged in as the AI user in a plain SSH terminal, only the root-owned token step (T1 login; refuses without a TTY or inside a Claude Code session) and the read-only lab check.

**PA-18 Hosts the AI user needs** (input for the network project; the AI host document lists them): `api.anthropic.com`, `platform.claude.com`, `claude.ai`, `github.com`, `api.github.com`, `code.claude.com`, and `downloads.claude.ai` only if the lab fetches the Claude Code engine itself (the lab setup PR records which applies). Managed settings disable claude.ai MCP connectors, nonessential traffic, and artifacts. (Follow-up R-2, section 13.3: this holds only where the managed file is in force; under an organisation policy that outranks it, those settings are the organisation's, and the user-level layer carries deny rules only, R2-O3.)

**PA-19 No onward SSH, no key access (PA-3 restated).** (a) Deny rules for the SSH client family and Read/Edit deny on `~/.ssh/**`. Proposed entries, the list that plan PR 3 implements in the three deny-list copies and the managed settings: `Bash(ssh *)`, `Bash(scp *)`, `Bash(sftp *)`, `Bash(rsync *)`, `Bash(ssh-keygen *)`, `Bash(ssh-add *)`, `Bash(ssh-agent *)`, `Read(~/.ssh/**)`, and `Edit(~/.ssh/**)`; how Claude Code's deny rules match variants (absolute paths, `env ssh`, wrappers) is not verified (section 12). (b) the LC-6 checks; (c) LC-11 and LC-13 on the server; (d) Claude Code never reaches the operator machine, the lab admin account, or the lab host. This replaces the repository rule "never try to reach the lab VM", which goes with the rewrite of `CLAUDE.md` (plan step 9).

**PA-20 Operator configuration** is the Ansible operator profile (PA-31), run by the operator admin from a clone the admin owns at a release tag; dry run by default; idempotent. On a fresh VM it applies the key rules of PA-16 to the operator user and the operator admin, with the operator user's `~/.ssh` in place of the AI user's. It installs archive prerequisites, sets the operator user without sudo, creates the output directories (PA-42), applies OC-10 only after a second login is confirmed, enables unattended security updates, installs the operator scripts per PA-42, prints the host key fingerprints, and ends by running the operator check. It never touches credentials, the operator user's output files, or production configuration, and writes nothing into a user's home.

**PA-21 Operator contract** OC-1 to OC-12 (ADR-012 section 5).

**PA-22 Operator script endpoints** are literals, listed in a configured allowlist read from the base commit (the GitHub API plus project-declared hosts); enforced by the operator code checks. It is carried by ADR-011 decision 11, which states it after this PR (it does not on `main`); ADR-012 does not repeat it (O-7). The allowlist is the policy input `operator_endpoints` (I-10).

**PA-23 ADR-011 is amended, not superseded.** Z7, OCI, alarms, lab access, and the Ubuntu operator profile are dropped. It keeps the rules for operator scripts (dry run by default, release tags, prompted credentials, sanitised output, standard-library Python) and refers to ADR-012 for the operator machine. Decisions cited by ADR-008 and ADR-009 keep their numbers.

**PA-24 ADR-005 is amended:** decisions 6 and 10 describe the Ansible lab and operator profiles on Debian 13, run by the admin users; decision 3 per PA-30; decision 5 stays; the amendment also covers decision 1's scope note, decision 7, section 1, the consequences, AC5-1, AC5-4, and AC5-6.

**PA-25 Deny entries of PA-19 in the template.** PA-19 and its deny entries go into the template's owned CLAUDE.md and required-deny list by a CR in the template repository.

**PA-26 Removal order is strict.** ARM64 is removed in two PRs: first from `architectures` and the runner labels in `config/project.yaml` with the arm64 job still running, then the job and the arm64 artifacts. (No `runner_labels` key exists in `config/project.yaml`: the labels are the `runner` and `runner_private` fields of each `architectures` entry. Code defaults that also name arm64 are `DEFAULT_ARCHITECTURES` in `scripts/pr_contract/config.py` and `DEFAULT_LABELS` in `scripts/checks/workflow_policy.py`; they change in the second PR, in this repository only, and the template keeps its own configuration listing amd64 and arm64 (round 4, O-24).) Narrowed by O-3 (round 2): the approver may cut a release tag at any PR boundary whose PA-A16 run is green, except between PR 5 and PR 6. The operator machine moves to a new tag only at or after PR 4. PA-A28 runs on a tag cut after PR 2 and is recorded in PR 3, which adds any permission PA-15 needs (C-1).

**PA-28 CI** applies the lab and operator profiles twice (the second run changes nothing) and once in dry run (the tree hash is unchanged), then runs the token step fixtures and both checks, in a pinned `debian:13` container (by digest) started with the two users and one key each (round 3, C-5); the release-tag pre-task has no bypass: the job runs the playbooks in a disposable clone whose local bare origin has `main` at the PR head and an unpushed local `v*` test tag on that commit, and a separate untagged-tree fixture shows the refusal (C-4); the aggregate `quality-gate` needs the job; required check names are unchanged.

**PA-30 This repository supports amd64 only.** The install engine and the manifest schema stay architecture-generic (ADR-008 decision 8); `scripts/toolchain check` requires artifacts for exactly the architectures listed in `config/project.yaml`; an artifact for an unlisted architecture is an error (O-4, round 2). Residual risk: the engine's arm64 path is tested only by the template's CI.

**PA-31 Lab setup and operator configuration are Ansible:** the CR-2 builder profile becomes the lab profile, the operator profile is retargeted to Debian 13, and both use one shared SSH hardening role.

**PA-34 Project toolchains on the AI lab** are installed by the lab admin with the root-owned `scripts/toolchain` from the platform's release tag, from the project's CI manifest read as "the tools CI uses" (ADR-008 decision 8 unchanged), into `/opt/ai-lab/project/`, amd64 only, with the checksum rules of the gate tools; dry run by default. A project package list of Debian archive packages, with no third-party apt sources, is applied by the lab admin through lab setup, only after the lab admin has read the dry-run output; the dry run prints every package name and version it would install (round 4, O-22). There is no package allowlist in v1: the lab admin's reading is the control (RR-P2). Inputs come from an anonymous clone at a merged commit or tag, or are extracted from the AI user's clone at a commit SHA the user supplies. Smoke tests of project tools run as the AI user, never as root. The project's own copy of `scripts/toolchain` is never executed.

**PA-36 Security updates:** lab setup and the operator configuration enable unattended Debian security updates; the operator admin schedules reboots of the operator machine; an AI lab is rebuilt rather than patched in place when a reboot is not enough.

**PA-37 T1 at disposal of an AI lab:** the disk is destroyed (G-18), so T1 is not rotated at disposal; its 90-day expiry and the ADR-001 rotation procedure stay.

**PA-38 ADR-004, ADR-006, and ADR-007 are withdrawn** in baseline v0.2; their numbers are not reused.

**PA-39 Zone Z8:** the lab host (jump host and hypervisor), outside the platform, with full control of the AI lab; recorded in ADR-012 and referenced from ADR-001 section 3.

**PA-40 Baseline v0.2 contains:** the constraints with zero cost restated without OCI (cited by ADR-009 decision 12); the component map (Windows client, per-project AI lab VMs, the operator machine, the lab host outside the platform, GitHub, Anthropic); the decision index with CHG-002, D2 to D7, D12, D15, and D16 superseded or reduced, and ADR-012 added; the sequence CR-57 implementation, Stage 5 (template), Stage 6 (first project on its own lab VM), Stage 7 (a timed rebuild test and metrics); PA-38.

**PA-42 Multi-project operator machine.** Each project's operator scripts are installed by the operator admin at that project's release tag into a root-owned directory per project; each project has its own output directory (mode 0700); runs are one at a time; T2 and T3 are created per run and limited to that project's repositories. **PA-43 Project non-production credentials** on an AI lab are entered by the user as the AI user in a plain SSH terminal, never in a Claude session; stored with file mode 0600; their names and paths are listed in the project's PROJECT.md, and the project's deny list blocks reads of those paths.

**PA-44 Pre-disposal mode.** The lab check has a read-only pre-disposal mode that lists every repository under `~/work` with uncommitted changes or unpushed commits; the user runs it before a lab is discarded.

**PA-45 Runbook.** Plan step 9 adds a new-project runbook: repository and rulesets (user), lab VM and lab setup (lab admin), token step (user), clone and `initialize-project` (Claude Code), operator script installation (operator admin), allowlist audit including the new repository (from this repository's `facts` with the read-only T3 of the PA-42 exception).

## 13. Follow-up R-2: a user-level deny layer for AI labs under an organisation policy

Added by design PR R-2 (branch `design/CR-57-r2-deny-layer`, Proposed, effective when that PR is merged). Docs-only; nothing is implemented, no setting changes. Labels: decisions PA-47 to PA-57, risks RR-P12 to RR-P15, open points R2-O1 to R2-O5, unverified items R2-N1 to R2-N6, lab item LC-16, criteria PA-A34 to PA-A38. They continue the numbering of this file; none is reused.

### 13.1 Why, and whether this is an amendment or a new CR

**Finding.** Plan PR 4 (PR 64, `impl/CR-57-operator-profile`, open) found on a real lab that `/etc/claude-code/managed-settings.json` is ignored by Claude Desktop SSH sessions: the user's organisation has a managed policy that outranks it, and the first managed source that delivers a policy key wins while the rest are ignored (managed settings page; the docs say `/status` names the source in use and the sources skipped, and that the opt-in `managedSourcesBehavior: "merge"` is a setting of the policy itself). The organisation policy cannot be changed. Trials on that lab: a deny rule in the managed file was ignored (`ssh -V` and `ssh-keygen -h` ran); the same rule in a project-level `.claude/settings.json` was refused; a deny rule in a plain user-level `~/.claude/settings.json` of the AI user was refused. So the lower scopes still apply under the policy. The project and the user file are owned by the AI user, who can change them. ADR-001 AC1-5 (managed or project settings deny the Section 5 commands, tested on each AI lab) is therefore not met on such a lab, and PA-5, PA-19, PA-A11, PA-A13, PA-A28 and the lab check item LC-4 all assumed that the managed file is in force.

**Amendment, not a new CR (recommendation; the approver confirms, O-28 of R-1 asked the same).** Reasons from the records: (1) the CR-57 design, ADR-012, ADR-001 section 5, the lab contract, the PA-28 job and the lab check are the things that change, and all are CR-57's; (2) ADR-003 section 4 says a needed design change after approval is a new **design PR**, not a new CR, and CR-39 (PR 42) and CR-57 R-1 (PR 59) amended merged designs and ADRs that way, with "Amended by" header rows that take effect on merge; (3) issue #57 stays open until plan PR 10, so the implementation PR of R-2 can declare `Implements: #57` and `Design:` this PR (rule PC-3 needs the design PR merged and linked to the same issue); (4) a new CR would need its own issue and would split one trust-model decision in two. This PR is therefore **follow-up R-2 of CR-57**, branch prefix `design/CR-57-`. It edits approved records, as R-1 did, only in the places listed in section 13.10. A new implementation row (plan PR 4a) carries the code.

### 13.2 Decisions

**PA-47 What the layer is.** Where an organisation policy outranks the managed file, the deny rules of the platform are also carried by the **user-level settings file of the AI user**, `~/.claude/settings.json`, written by lab setup, owned by root, mode 0644, and made unchangeable with the immutable file attribute (`chattr +i`, FS_IMMUTABLE_FL). The file holds exactly `{"permissions": {"deny": [...]}}`, the entries of the lab-wide deny list in the order of `workspace/claude-user/required-deny.txt` (90 entries at this revision), as canonical JSON (two-space indent, final newline). It holds no other key: the managed-only keys (`allowManaged*`) have no effect there, the other managed keys (PA-18: connectors, traffic, artifacts) are not claimed under a policy (R2-O3), and a minimal file keeps the content check of LC-16 exact. Deny arrays merge across scopes and an allow rule in any scope cannot override a deny (permissions page), so the layer cannot be relaxed by a project or local file.

**PA-48 Why the attribute, and why not a root-owned directory.** The AI user owns `~/.claude` because Claude Desktop deploys its engine under `~/.claude/remote/` and Claude Code writes its own state there; a root-owned `~/.claude` is therefore not workable (alternative D). In a directory the AI user owns, a root-owned file can still be unlinked or renamed, so root ownership alone is not enough. With the immutable attribute, write, truncate, unlink, rename, link, chmod and chown on the file fail with `EPERM`, and clearing the attribute needs `CAP_LINUX_IMMUTABLE`, which the AI user does not have (LC-2: no sudo, no root-equivalent group).

**PA-49 The known sidestep, stated rather than hidden.** The attribute protects the file, not its parent. The AI user owns `~/.claude` and `~`, so it can rename the directory (`mv ~/.claude ~/.claude.moved`), create a new one with no deny list, and start a new session or engine against it. Immutability of the directory itself would stop this and also stop Desktop and Claude Code from creating files in it (alternative E). The layer is therefore a **guard against accidental and ordinary changes, against Claude Code's own edit tools, and against a project or local file relaxing a rule; it is not a barrier against an AI user that runs shell commands on purpose** (RR-P12). LC-16 reports the missing file after the fact and warns on a moved directory (heuristic); a running session may or may not drop its rules when the file disappears (R2-N2).

**PA-50 The write is the one exception to "nothing is written into a user's home", and it is written defensively.** ADR-012 decision 5 and PA-16 say lab setup "writes nothing into a user's home" and PA-A11 and PA-A29 test that, with a planted symbolic link. The layer needs exactly two paths in the AI user's home: `~/.claude` (created when missing, owned by the AI user, mode 0700) and `~/.claude/settings.json`. Nothing else in any home, never the lab admin's home (LC-3: no `~/.claude` there), never a recursive operation. A root process writing into a directory the AI user controls is a classic link attack, so the write is done by one purpose-built Ansible module (standard-library Python, run as root, no shell, no `chattr` command, no Ansible `file` or `copy` module on these paths) that works on file descriptors, not paths:

1. Read the AI user's home from the account database, never from the environment. `lstat` it: a real directory owned by the AI user, else refuse. Open it with `O_DIRECTORY|O_NOFOLLOW` and keep the descriptor.
2. `openat` `.claude` with `O_DIRECTORY|O_NOFOLLOW`. A symbolic link or a non-directory: refuse. Missing: `mkdirat` mode 0700, open it the same way, `fchown` to the AI user. Check the descriptor with `fstat` (a directory owned by the AI user).
3. Inspect `settings.json` through the directory descriptor (`fstatat` without following). Absent: continue. A regular file owned by root with link count 1, the immutable attribute set and equal content: nothing to do (idempotent, no change reported). The same file with different content: clear the attribute through its descriptor, replace, set it again. Anything else (a symbolic link, a hard-linked file, a file the AI user owns, a directory, a device): **refuse and name the account and the path**; the lab admin decides, nothing is removed or moved (decision 5: removes nothing).
4. Write the new content to a temporary name in the directory (`O_CREAT|O_EXCL|O_NOFOLLOW`, mode 0600), `fchown` root:root, `fchmod` 0644, `fsync`, `renameat` onto `settings.json`, reopen it with `O_NOFOLLOW`, check that it is the same inode, set the attribute with `ioctl(FS_IOC_SETFLAGS)` on that descriptor and read it back.
5. Every step after the first two uses the two descriptors, so an AI user that renames `~/.claude` or swaps in a link while the play runs cannot redirect root: the write lands in the directory inode that was checked.
6. A dry run reads and reports, and writes nothing. A failed attribute call after the rename removes the new file again (`unlinkat`) and fails, so no root-owned file that the AI user could delete is ever left looking protected (PA-51).

There is a short window in which the file is replaced without the attribute on a second run with changed content. It exists only at lab setup, which the lab admin runs, and an old file stays in force until the rename.

**PA-51 Filesystems and what happens without support.** Support is decided by trying, never by the filesystem name. The attribute is available through `FS_IOC_SETFLAGS` on ext2/3/4, xfs, btrfs, f2fs and jfs, which covers the Debian 13 default (ext4); tmpfs and overlayfs depend on the kernel; NFS, CIFS, FAT and exFAT, NTFS drivers, and most FUSE and 9p mounts do not support it; and without `CAP_LINUX_IMMUTABLE` even root cannot set it (the default of Docker, Podman and many LXC setups). This is general kernel knowledge and is not verified on any lab (R2-N3); the real lab's answer is part of the approver check (PA-A38, step A1). When the attribute cannot be set, lab setup in mode `both` or `user` **fails closed**: it removes the file it just placed, leaves nothing behind, and says that the filesystem of the home directory does not support the attribute (or that the capability is missing) and which errno came back. The lab admin then (a) moves the home to a supported filesystem at provisioning, or (b) selects mode `managed` and accepts that the deny rules depend on the managed file being effective, which the approver check shows is not so under an organisation policy. No other fallback is designed: no bind mount, no loop image, no relocation of the directory (alternatives F and G).

**PA-52 Modes.** Lab setup gets one variable, `lab_deny_layer`, with the values `both`, `user`, and `managed`, written to `lab.conf` as `deny_layer=<value>` so the lab check reads what the lab admin chose. `managed` is today's behaviour (the managed file only; the fallback for hosts without an organisation policy and for homes on a filesystem without the attribute). `user` writes only the user-level layer. `both` writes both. **Recommendation: `both` is the default** (R2-O1): the lab admin cannot see from the machine whether an organisation policy applies, and a wrong guess would leave a lab with no effective deny rule; `both` costs the home-write exception and the attribute on every lab, and `managed` stays one explicit variable away. A lab setup that finds no support for the attribute therefore stops by default (PA-51). The managed file stays in every mode that writes it, so LC-4 is unchanged; LC-4 passes on an organisation-policy lab because the file is present, and no OS check can see that it is ignored, which is why the approver check exists.

**PA-53 When Claude Code cannot write the file.** The docs say that when the user-level file is not writable a setting changed with `/config` or `/model` applies to the current session and is lost in the next, and describe no warning; the "always allow" choice writes to `.claude/settings.local.json`, not the user file; which file `/hooks` writes is not documented; reads are unaffected. Expected effect: the AI user cannot persist user-level preferences through `settings.json`, and Claude Code does not fail to start. This is read from the docs and **not run** (R2-N1); the approver check records what the session does (PA-A38, step B5).

**PA-54 Lab check item LC-16 (checked, read-only, run as the AI user).** In modes `both` and `user` it fails unless all of these hold: `~/.claude` is a real directory (not a link) owned by the AI user; `~/.claude/settings.json` is a regular file, not a link, link count 1, owner root:root, mode 0644; the immutable attribute is set (read with `FS_IOC_GETFLAGS` on a descriptor opened with `O_RDONLY|O_NOFOLLOW`, which needs no privilege; an unsupported answer is a failure); and the parsed content equals exactly `{"permissions": {"deny": <the lab-wide deny list>}}`, entry for entry and in order, with no extra key. It warns on a directory named `.claude.*` in the home (a possible moved `~/.claude`; a heuristic, a renamed directory can have any name). In mode `managed` it passes and says the layer was not selected. It prints names and rules only, never the file's content, and changes nothing (the existing tree-hash assertion of PA-A8 covers it). The reference is the root-owned **lab-wide deny list** `<lab tools dir>/deny.txt` that lab setup installs next to `lab.conf`: a byte copy of `required-deny.txt` now, and from plan PR 8 the core list plus the project's `deny.platform.txt` entries, so one file feeds the managed settings, the user-level layer and LC-16 and no project credential-path entry (PA-43, I-7) is missing from the effective layer. LC-5 stays undefined.

**PA-55 Drift.** The source of truth of the layer is `workspace/claude-user/required-deny.txt`, not the user-level `settings.json` of the workspace restore (a different file with the same name). Next to the existing three-copy drift test (`.claude/settings.json`, `required-deny.txt`, `workspace/claude-user/settings.json`: `tests/lab/test_deny_drift.py` and, until plan PR 7, lines 390-394 of `tests/workspace/run.sh`) the implementation PR adds a test that the role takes its list from `required-deny.txt`, that the generated JSON has the same entries as each of the three copies and the same count (90), and that no entry is listed twice; the PA-28 job compares the installed `deny.txt` and the installed layer with the repository copy.

**PA-56 What CI can and cannot show (PA-28 job).** The `host-profiles` job runs lab setup in a `debian:13` container that may lack `CAP_LINUX_IMMUTABLE` and whose filesystem is overlayfs. Without the attribute, the following still run: the module's unit tests with seams for the ownership and attribute calls, the refusals of PA-50, content, idempotency and the dry run, LC-16 against a fake machine with the flag read through a seam, and the drift test. In the job, a **probe step** first tries `chattr +i` on a scratch file in the same filesystem as `/home`. If it works (the job is started with `--cap-add LINUX_IMMUTABLE`, and if overlayfs still refuses, with a loop-mounted ext4 image on the home directory in a privileged container; the implementation PR picks the first that works, states it in its PC-6 section, and uses the lightest), the real tests run as the AI user: write, append, truncate, `rm`, `mv`, `ln`, `chmod` and `chattr -i` on the file all fail; the second run changes nothing; LC-16 passes; and each `chattr -i` as root followed by a change makes LC-16 fail for that change. If the probe fails, the step prints `immutability not testable here: <errno>`, runs the fail-closed fixture of PA-51 (mode `both` must fail, leave no file and name the errno, which is testable without the attribute), and the job's summary says the real attribute is proved only by the approver check. It never ends green by skipping silently. What no container can prove: that a real Claude Desktop session under an organisation policy honours the layer, the attribute on the real lab's filesystem, and the sidestep of PA-49.

**PA-57 Approver check PA-A38.** Exact commands and yes/no results are in the acceptance criteria. It runs on the first real lab setup from a tag that contains plan PR 4a, in a Desktop session opened in a folder with no project settings, and replaces for such a lab the "honours a managed deny rule" part of PA-A28.

### 13.3 Relation to the managed-file layer

The managed file stays: it is the layer for hosts without an organisation policy, it carries the keys the user-level file does not (PA-18 connectors, nonessential traffic, artifacts, bypass mode), and LC-4 keeps checking it. The user-level layer adds nothing a working managed file lacks; under an organisation policy it is the only deny layer the platform controls that the AI user cannot edit with the tools Claude Code gives it. PA-5 now reads: on the AI lab the guardrails live in the managed settings and, where an organisation policy outranks them, in the user-level deny layer. PA-18's last sentence ("Managed settings disable claude.ai MCP connectors, nonessential traffic, and artifacts") holds only where the managed file is in force; under a policy those settings are the organisation's. `permissions.disableBypassPermissionsMode` and `enableAllProjectMcpServers` are documented as valid in any settings file, so they could ride the same file (R2-O3). If an organisation ever sets `allowManagedPermissionRulesOnly`, user-level rules are ignored and this layer stops working; the trial above shows that this policy does not set it, and PA-A38 detects it on any other lab.

### 13.4 Alternatives considered and rejected

| ID | Alternative | Why rejected |
|---|---|---|
| A | Change the organisation policy, or ask for the managed file to be honoured | Not possible (given). The opt-in `managedSourcesBehavior: "merge"` is a key of the policy, so it is the organisation's to set |
| B | Operating-system restrictions alone (for example mode 0750 on the SSH client binaries, AppArmor) | Can stop the SSH client family if the binaries are not executable for the AI user. Cannot cover the `gh` rows of ADR-001 section 5, because the same user holds T1 in `~/.config/gh/` and can read it and call the API with any HTTP client; a same-user token read cannot be prevented at OS level. Kept as a possible complement (R2-O4), not a replacement |
| C | Project-level `.claude/settings.json` as the only layer | Refused correctly in the trial, but owned by the AI user. It stays as the second layer (reviewed through the PR and the `deny-list` gate check) and is not enough for AC1-5 |
| D | Root-owned `~/.claude` with writable subdirectories | Desktop deploys under `~/.claude/remote/` and Claude Code writes top-level state; the set of names changes between versions, so a missing name fails silently or breaks sessions. Not workable (as the request assumed) |
| E | Immutable attribute on the directory `~/.claude` | Closes the PA-49 sidestep but blocks every create and delete inside it, with the same problem as D |
| F | Read-only bind mount of a root-owned file over `~/.claude/settings.json` | Needs a mount-point file inside the AI-owned directory (the same PA-11 conflict), a boot-time unit, and `CAP_SYS_ADMIN` (not in containers); the mount follows the renamed directory, so PA-49 applies equally. No gain over the attribute |
| G | `CLAUDE_CONFIG_DIR` set through `SetEnv` in sshd to a root-controlled directory | The directory holds session state and must be writable by the AI user, so the settings file inside has the same problem; Desktop's own deployment path under it is undocumented; changes the sshd contract (LC-13). The AI user can also start another process without the variable |
| H | A `PreToolUse` hook in the same file that runs a root-owned script | Stronger matching than patterns, same carrier and same sidestep. Out of scope (R2-O4) |
| I | A credential broker that runs as another user so the AI user cannot read T1 | The only real answer to a same-user token read; a CR of its own, not decided here |
| J | Accept project-level files only and weaken AC1-5 | Leaves the Section 5 commands to a file the AI user edits |

### 13.5 Recommendation

Adopt the user-level immutable deny layer (PA-47 to PA-57), default `both`, with the managed file kept, on these conditions: the write is the defensive module of PA-50 and nothing else in a home; support is decided by trial and fails closed; LC-16 and the PA-28 steps ship in the same PR (plan PR 4a); and the residuals RR-P12 to RR-P15 are accepted in writing, because the layer is a guard against ordinary change and not against an AI user that uses its shell. Before relying on AC1-5 for a lab, the approver runs PA-A38 on it.

### 13.6 Risks and residuals

| ID | Statement |
|---|---|
| RR-P12 | Accepted: an AI user with a shell can rename `~/.claude` and start Claude Code or another tool without the deny list (PA-49), start any other program, or use `CLAUDE_CONFIG_DIR`.
