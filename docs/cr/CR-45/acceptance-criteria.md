# CR-45 Acceptance criteria

Verified by the implementation PRs in `ai-software-template` (see the plan). "CI" means a green run of the named template job. "Gate check" means a check of `./scripts/quality-gate.sh` with a passing fixture and failing fixtures. A "documented manual measurement" names its procedure in the evidence column. The criteria become binding when the design PR is merged; those that depend on a question for the approver follow its decision.

| ID | Criterion | Evidence |
|---|---|---|
| M-1 | `.template/budgets.toml` holds the classes and values decided in design section 4.1 (lines, bytes, description characters, the always-loaded group, `[outputs]`, `[regression]`). `size-budget` reads every value from it: a file over its line or byte limit, and a description over its character limit, fails with `path: <n> > <max>`; a file within passes; changing a value in the file changes the outcome with no code change; a class without a file passes. A `[[budget]]` entry (`class`, `key`, `value`, `reason`, `pr`) in `.template/overrides.toml` raises that one value and the check prints `raise: <class>.<key> <old> -> <new> (<pr>)`; a whole-file override of `budgets.toml` fails; `template-sync` lists each active raise in the sync PR body. | Gate check `size-budget`, one failing fixture per class and per limit, a fixture that changes a value, and fixtures for a per-key raise (printed, applied), an entry with a missing field, and a whole-file override (fails); a `template-sync` fixture with an active raise |
| M-2 | `size-budget` computes the always-loaded set (`CLAUDE.md`, its two imports, rules without path scoping, Skill names and descriptions) and fails above its group limit; a rule with path scoping is not counted; the check prints the set's bytes and `ceil(bytes / 4)` as an indication. | Gate check fixtures: over the limit, scoped rule excluded, unscoped rule included |
| M-3 | Gate check `skill-layout` fails a `SKILL.md` without the headings `Reads (in order)`, `Does not read`, and `Report`, with an empty one of them, or with no script named; each of the eight Skills passes. | Gate check fixtures; the eight Skills in the template |
| M-4 | `output-budget` runs each script with a fixture on it and fails when the output is larger than its `[outputs]` value; every script ends with one summary line starting `<script>: ` of at most 120 ASCII characters; a script without a fixture or without the line fails. | Gate check fixtures, one oversize and one missing-line case |
| M-5 | Concise CI output: the gate prints at most 20 findings per check with each cut at 200 characters (not bytes: a multibyte fixture stays valid UTF-8); under `GITHUB_ACTIONS=true` it prints one `::error` annotation per failed check, at most 10, the tenth naming the remaining IDs; locally it prints none. Escaping follows `sanitize()`: in the message `%`, CR, LF become `%25`, `%0D`, `%0A`; in properties also `:` and `,` become `%3A` and `%2C`. `pr-contract` reports its failures as annotations under the same rule, at most 10. The fallback in `pr-checkpoint show` keeps only `FAIL` lines and the indented lines under them from the failing job's log, sanitised, at most 10; no raw log is printed. On a test PR with a deliberate failure the annotations are readable through `gh api` as the machine account (verification item V-3). | Gate fixtures with and without `GITHUB_ACTIONS`, with `%`, CR, LF, `:`, `,` and multibyte text in findings and in a check ID; a `pr-contract` fixture with more than 10 failures; a log fixture for the fallback; **documented manual measurement:** push a failing test PR, run `gh api repos/<owner>/<repo>/check-runs/<id>/annotations`, record the count, the first message, and the per-step limit in the PR; if V-3 fails, record that the filtered log is the primary channel |
| M-6 | `pr-checkpoint` accepts only the format of design section 7.1 between the markers (checklist lines, at most 20 items, 120 characters each, 2 KiB, optional `(ID, ...)`, optional `; blocked: <reason>`); a violation stops with the line number and repairs nothing; `tick` edits only the text between the markers. | Fixture tests: one passing block and one failing block per rule |
| M-7 | `pr-checkpoint show` prints the counts, the next (first unticked) item, the result per CI job with the annotation text of failed jobs, at most 10 commits since the merge base, and at most 3 `ci-failed` lines followed by `ci-failed: +<n> more` when more jobs failed, within its `[outputs]` limit on the maximal fixture (20 commits, 5 failed jobs); the text after `ci-failed:` is CI data and the `resume-work` `SKILL.md` says so; it prints no comment, review thread, author, or raw log; a missing or malformed block makes it exit non-zero with a report. The `resume-work` `SKILL.md` lists what it must not read. | Fixture test on a maximal PR; `skill-layout` on `resume-work` |
| M-8 | `cr-context` prints the CR `README.md`, then each other file with lines, bytes, and its `##` headings with line numbers, within its `[outputs]` limit on a five-file, 14-heading fixture; it never prints another file's body. | Fixture test |
| M-9 | `review-threads` prints unresolved threads only (outdated flagged), 5 per page, with `--page <n>`, the count of the remaining threads, and the counts of excluded items by reason; it never truncates an approver's text (a fixture item of 3 KiB is printed whole); the T-11 filters are unchanged. | Fixture tests with 12 threads and one long item; the T-11 fixtures still pass |
| M-10 | The owned `CLAUDE.md` of the template contains the numbers of design section 8 (a range of at most 100 lines and 8 KiB, no whole read of a file over 200 lines or 8 KiB, 40-line output) and stays within its budget; this repository's `CLAUDE.md` carries them after the change PR (Q7). Compliance by Claude Code is **not** gated. | Gate check `claude-md` (hash) and `size-budget`; the change PR diff. Behaviour is visible only in tier C figures, if the user supplies them |
| M-11 | `metrics static` prints tier A for a tree, deterministically (the same tree gives byte-identical output), offline, with no login, name, email, or token in the output. | Fixture test run twice and compared; `leak` scan of the output |
| M-12 | `metrics prs` computes the tier B values of design section 10.3 from PR data fixtures, prints counts and medians only, refuses to print a median over fewer than `min_prs` PRs without the word "indicative", prints no login or name, and makes no call other than `gh api` GET. | Fixture JSON for PRs with rounds, pushes after ready, and failing first runs; static check of the script's calls (`forbidden-api` passes) |
| M-13 | `metrics snapshot --label <l>` writes `docs/metrics/<l>.toml` in the schema of design section 10.3 with numbers, PR numbers, and the label only, and refuses to overwrite; `metrics compare <a> <b>` prints each value that crosses a `[regression]` threshold and exits 1, or exits 0 with none. | Fixture tests: a snapshot pair with and without a regression; the written file passes `public-repo-hygiene` |
| M-14 | The `[usage.<pr>]` table is optional: a snapshot without it is valid; a snapshot with it is validated (integers, keys from the fixed list, no other text); no script in the template reads Claude Desktop, a session transcript, or any path outside the repository. | Fixture tests; static check of `scripts/metrics` reads and calls |
| M-15 | The design's constraints hold in the template: no workflow runs `scripts/metrics` or any script of this CR, none has a schedule or an event trigger for it, none invokes Claude; no new credential, MCP server, or telemetry service; `docs/metrics/` files pass the hygiene patterns. | `workflow-policy` and `no-claude-in-workflows` on the template's workflows; a checklist in the last implementation PR; `leak` job on a generated tree |
| M-16 | **Baseline.** (a) The static baseline snapshot `baseline-static` is committed in the last implementation PR (Stage 5 exit) and covers the template and a generated repository; (b) the full baseline `baseline` (tiers A and B over the PRs of one full Class 3 CR, tier C if supplied) is recorded at Stage 7 and its soft thresholds are re-confirmed by the approver. (b) is **open until Stage 7** and recorded as such. | (a) the committed file and `metrics compare baseline-static <label>` returning 0 on a clean tree; (b) the approver's review of the baseline PR at Stage 7 |
| M-17 | The verification items V-1 to V-3 of design section 14 are checked against current Claude Code and GitHub behaviour and the result is recorded in the PR that depends on them (PR 1: V-1 and V-2, PR 2: V-3); the real always-loaded set of the template is measured and the limits of design section 4 are reconfirmed or changed with the numbers shown. | **Documented manual measurement:** `./scripts/quality-gate.sh` output of `size-budget` for the generated repository, pasted in PR 1; the documentation pages and dates consulted, listed in the PR |

Entry to Stage 5 also needs ADR-008 and ADR-009 approved. This CR delivers ADR-010 only, and none of these criteria covers the other two.
